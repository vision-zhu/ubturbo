# SMAP 性能测试指南

## 目的

本指南用于比较启用 SMAP 前后的容量收益、业务性能和迁移开销。测试结果只对记录的硬件、内核、
页面类型、NUMA 拓扑、配置和负载有效，不能外推为所有环境的性能保证。

## 必须记录的环境

| 类别 | 内容 |
| --- | --- |
| 硬件 | CPU/芯片型号、节点数、内存层级、互联类型 |
| 软件 | openEuler 版本、内核、GCC、SMAP/UBTurbo 版本 |
| 拓扑 | local/remote NUMA ID、容量、CPU affinity |
| 页面 | 4K 或 2M、透明大页和静态大页配置 |
| SMAP | 扫描方式、扫描周期、迁移周期、阈值、迁移模式 |
| 负载 | 软件版本、数据集、并发、预热和运行时长 |

缺少上述信息的图表不能进入 README 或发布说明。

## 对照设计

至少包含：

1. 本地内存充足、SMAP 未迁移的基线。
2. 同一硬件限制下关闭 SMAP 策略的容量受限基线。
3. 启用 SMAP 的实验组。
4. 每组不少于三次有效重复，报告中位数和离散程度。

除待比较的 SMAP 参数外，CPU 绑定、内存容量、负载、数据集和网络设置必须一致。不要在实验组单独
应用额外系统调优。

## 指标

- 业务吞吐、时延及尾时延。
- 本地/远端页面量、迁出/迁回量和迁移失败量。
- 扫描 CPU 占用、迁移 CPU 占用和内核时间。
- 互联带宽及业务带宽竞争。
- 从目标下发到页面比例收敛的时间。
- 应用错误、超时、OOM 和迁移期间最大性能抖动。

带宽单位必须注明采用 GB/s（10^9 B/s）还是 GiB/s（2^30 B/s）。百分比必须说明分母和采样窗口。

## 测试流程

1. 记录并固定内核、模块、服务和配置版本。
2. 清理上一轮进程和 SMAP 状态；只有确认没有使用者后才清理共享状态文件。
3. 固定 CPU/NUMA 绑定，准备一致的数据集并完成预热。
4. 运行基线并采集业务、系统和 SMAP 指标。
5. 启用 SMAP，等待配置和页面比例稳定后运行实验组。
6. 重复测试并保存原始日志、命令、时间戳和配置快照。
7. 分析异常值；不得只删除对结论不利的有效样本。

## 工作负载注意事项

### Redis

- 明确数据持久化、淘汰策略、pipeline、客户端线程和 key/value 分布。
- 每轮使用同一预热与数据装载方法。
- 报告吞吐的同时报告 P99/P999 时延。

### MySQL

- 明确存储引擎、buffer pool、数据集、读写比例和 checkpoint 状态。
- 客户端与服务端的 CPU、NUMA 和网络绑定保持一致。
- 不应把 page cache 或数据库缓存的冷热启动差异归因于 SMAP。

### SPEC CPU

- 记录具体套件、编译配置、运行副本数和报告规则。
- 仓库提供的 [`speccpu-gcc-best.cfg`](../../../docs/resource/speccpu-gcc-best.cfg) 只是配置参考，使用前
  必须核对目标工具链和许可证要求。

### STREAM

- 报告数组大小、线程数、NUMA 绑定和单位。
- 数组必须大于相关缓存层，且运行时间足以覆盖迁移后的稳定阶段。

## 报告要求

每个结果必须附带可复现命令、原始数据路径、环境表、基线定义和误差说明。只有具备这些材料的结果
才能转化为项目性能声明；概念示意图不得标注为实测结果。
